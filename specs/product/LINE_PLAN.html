Plan · QuiQui line · Nov 2026

Nine QuiQui games, one core

One QuiQui game for each kind of TutoTOONS game. All nine run on the same scene player and template library. What differs is scene data, the hub, and a few game-specific modules. Each game is matched to the closest TutoTOONS title so we copy shape from something that exists.

All ids and file names are English, as decided for the restart. Waves and template names follow specs/product/SCOPE_LATEST.yaml in big-quiqui-v2, now a frozen reference. This is a plan, not an approved spec. Each game still needs its own scope, slices and tasks before code.

Diagram 2 · Common architecture

What every game shares

Everything in the red part is the same code in all nine games. Everything in the gold part is written per game. The core is a Godot addon, quiqui_core.

AreaCommon, in the coreSpecific, in each game
ServicesLog, ProgressManager (atomic save), AudioManager, SceneManager, FsmSave schema gets a game section. Same save file rules.
Scene playerScenePlayer, StepRunner, SceneDef and StepDef resourcesNone. Games only write data.
GesturesGive→Receive, Rub, Tap, Pan, Steer and the three modifiersNone. A new gesture goes to the core, not to a game.
TemplatesAll 28 buildable Builder templates, in three wavesNew templates start as x_* in one game. They move to the core once a second game needs them.
CharacterQuiQuiRig and the reaction vocabularyEach game adds its own poses and friends.
TeachingGhost hand, gentle miss, hint queueNone.
LanguageEnglish ids, voice by key, locale foldersEach game records its own voice lines.
QualityGUT, TouchSim, GeometryOracle, preflight gates, size barsEach game adds scene-level tests on its own data.
ContentArt style rules in DESIGN.mdBackgrounds, props, friends, songs, recipes. All per game.

Diagram 4 · Repositories

One repository per game, plus a core

Decided on 2026-11-09. The local folders mirror GitHub, so each repository is one folder next to the others.

~/Developer/                      mirrors github.com/danielvm-git, one folder per repo
  big-quiqui-cleanup/            game 1. A new repository with its own specs. The core starts here
    game/addons/quiqui_core/     isolated module. Core code may not reference game code
    specs/product/GAME_PLAN.html plan for the game
    specs/product/LINE_PLAN.html this general plan, canonical copy
  big-quiqui-core/               created when Care starts: the addon extracted with git subtree split, plus shared tooling
    addons/quiqui_core/
    VERSION                      tagged releases, v1.0.0 and up
  big-quiqui-care/               game 2. A new repository that consumes the core as a git submodule
    game/addons/quiqui_core/     git submodule, pinned to a core tag
  big-quiqui-story/ -salon/ -adventure/ -kitchen/ -dance/ -flusier/ -town/    games 3 to 9, created when their turn comes

frozen reference: big-quiqui-v2 (the e12 and e13 prototype and the 17 old rooms)
not part of the line: big-quiqui (v1), big-quiqui-fable (reboot), big-quiqui-retro (MakeCode demake)
  • The core is born inside CleanupDo not design a shared library first. The simplest game builds the player and the wave-1 templates, with a hard boundary: core code may not reference game code.
  • Extract when Care startsThe addon moves to big-quiqui-core with its history kept (git subtree split). Two real users shape the interface better than one.
  • Each game pins a core tagGames consume the core as a git submodule at game/addons/quiqui_core. A fix in the core reaches a game only when it upgrades, so shipped games stay stable. The central CI must check out submodules. That is not verified yet.
  • New templates start inside one gameAn x_* template lives in its game and moves to the core when a second game needs it.
  • Why not one repositoryThe release tool and the central CI work per repository with one tag format and one version ladder. Nine apps in one repository would need tags per path.
  • Repositories are created lateA game's repository is created when the game starts. Until then its folder holds only its plan page.

The rule: sort by new templates, then wave 2 and 3 templates, then own modules, then templates used. Three calls are judgment, not count. Adventure comes before Kitchen, because its seven library templates have evidence and need no new engine, while Kitchen needs a new template with the weakest evidence. Kitchen comes before Dance, Flusier and Town, because its new piece is a plain drag-and-order step, while those three each add an engine-sized piece: audio timing, a multi-pet rig with a collection save, and a walking world with a saved layout. Dance comes before Flusier, because the rhythm engine stays inside three scenes, while Flusier touches the rig, the save and the templates. Town is last: the walking world plus a saved layout is the largest piece in the line.

Rules for every game

The same charter, nine times

  • Ages 4 to 7No reading needed. Every prompt is a picture plus a voice or sound.
  • Offline, no ads, no telemetryNo network call in any game. Nothing leaves the device.
  • No punishmentNo lives, no game over, no timer that ends a step. A miss returns the item.
  • Family voiceVoice is recorded by the family in PT-BR first. Locales are folders, not code.
  • English idsCode, data keys and file names are English. Only voice and parent-area text are translated.
  • Same art styleGlossy, candy-colored, no pure-black outlines. One style guide across the line.
Decisions

What is decided and what is open

  • Decided · build orderCleanup, Care, Story, Salon, Adventure, Kitchen, Dance, Flusier, Town. From the simplest to the most complex, by the rule in the build order section.
  • Decided · a fresh startA new repository per game, each with its own specs. big-quiqui-v2 is frozen as the reference: its e12 and e13 work is the prototype of the player and the templates, and e14 to e16 are not continued there.
  • Decided · the 17 old roomsThey are not migrated inside big-quiqui-v2. Each game rebuilds the rooms it needs, as data, in its own repository. Care rebuilds the care rooms (about 11). Rooms such as vila, mercado, casinha and festa (Town), pinguim_jogo (Adventure) and pato_danca (Dance) come with those games.
  • Decided · nine appsSeparate apps, no launcher.
  • Decided · progressCoins and stars stay separate in each game.
  • Decided · repositoriesOne repository per game plus big-quiqui-core. The first repository is big-quiqui-cleanup, with the core as an isolated module. big-quiqui-core is created when Care starts.
  • Decided · big-quiqui-flusierIt is the ninth game: pets in rooms, in the style of Fluvsies. It shares the pet care and collect type with Care, but it is Form C. Its name follows the folder and can change.
